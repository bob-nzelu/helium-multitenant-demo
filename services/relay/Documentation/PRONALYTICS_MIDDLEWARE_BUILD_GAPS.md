# Pronalytics Middleware API — Build Gaps (internal)

Companion to `PRONALYTICS_MIDDLEWARE_API.md`. That document describes the **target external contract** we commit to integrators. This list is the delta between that contract and what the canonical code does **today** — i.e. what HeartBeat/Relay must build so the published doc is true. **Not for external distribution.**

Grounding: HeartBeat `helium-services` @ `master`; Relay `helium-multitenant-demo/services/relay` @ `origin/main`. Each gap cites the doc section it backs.

**ARCH ratification:** ARCH confirmed the spec shape and fanned out build chips on 2026-06-15. Authoritative record: `helium-services/docs/parallel_sessions_2026_06_12_BACKEND_RR/EXTERNAL_INGESTION_ALIGNMENT_2026_06_15.md` (commit `7f72226`). Rulings locked there supersede any earlier draft language.

| # | Doc §  | Contract says | Today | Build owner |
|---|--------|---------------|-------|-------------|
| 1 | §2 Auth | External auth is **OAuth 2.0 `client_credentials`** against HeartBeat: `POST /api/auth/oauth/token`, JWKS at `/.well-known/jwks.json`, EdDSA JWT `aud=helium.relay-ingest`, `expires_in=900`, admin client-registration endpoints. | **Spec-only, unbuilt.** `EXTERNAL_SERVICE_OAUTH_SPEC.md` is LOCKED but lives on unmerged branch `feat/external-service-oauth-spec` (1 `.md`, 0 `.py`). PR #120 (O1–O4) OPEN. No `/oauth/token`, no JWKS, no `oauth` schema in `master`. | **HeartBeat** |
| 2 | §2.3 Auth | **Relay validates the `aud=helium.relay-ingest` bearer JWT locally** (cached JWKS) on the ingest/status path. | Relay's bearer path is the **user-introspect** path only (`deps._verify_user_jwt` → HB `/introspect`). No `aud`-routing, no JWKS cache, no external-token validation. (HMAC is the only other external path.) | **Relay** |
| 3 | §3.1–3.3 Ingest | One `/api/ingest` call accepts a **JSON array of N invoice records** and returns a **per-invoice result** (`processed[]/duplicates[]/failed[]` + `summary`), **one IRN + QR per invoice**. | Relay's external flow ingests file bytes and returns a **single** `IngestResponse` (one `irn`/`qr_code` for the whole upload). No array parsing, no per-record fan-out, no batch-summary envelope. (The per-record batch processor existed only in the retired `helium-abmfb-demo`.) | **Relay** |
| 4 | §3.3 Ingest | **A QR code is returned for every invoice** in a multi-invoice ERP submission. | Only the single-document external flow returns a QR; there is no per-record QR for a batch. | **Relay** |
| 5 | §4 Status | **`POST /api/status`** on Relay: look up by `transaction_id` / `irn` / `batch_id`; returns per-invoice middleware `result` + `firs_status`. | **No status endpoint on Relay.** Building blocks exist — HeartBeat `POST /api/v1/heartbeat/blob/status` + `batch_state` give blob/batch status — but Core can only resolve an invoice by **internal `invoice_id`/`queue_id`, not by IRN/`transaction_id`**. Prereq: Core needs an **`external_transaction_id` column** (additive) on `invoices.invoices`, populated at ingest time from the ERP's `transaction_id`, enabling round-trip lookup. ARCH-confirmed 2026-06-15. | **Relay** (endpoint) + **Core** (`external_transaction_id` column + by-IRN/by-txn lookup) |
| 6 | §5 AMQP | External systems may submit the **same payload over AMQP** to a per-tenant Relay ingestion exchange/queue; results to a reply queue + `/api/status`. | **No AMQP ingestion in Relay** (grep: only `queue_id` naming; no `aio_pika`/`pika`/consumer). RabbitMQ in compose is Core↔Edge internal only. Needs: a Relay AMQP consumer, the per-tenant exchange/queue/routing-key contract, and a reply-queue result path. | **Relay** |
| 7 | §3.2 Ingest | VAT is **caller-supplied and required** (`vat_amount`); fields may be **per-tenant remapped** at onboarding. | The flat field map + per-tenant `fields`/`format_type` exist in `tenant.py`, but the external flow does not parse/validate per-record fields or VAT (that logic lived in the abmfb-demo). Confirm the field-mapping seam is wired for the canonical Relay. | **Relay** |
| 8 | §3.3 Ingest (IRN) | IRN is FIRS-correct, using the tenant's **`firs_service_id`** (e.g. `B673FBAF` for AB Microfinance). | `irn.py` inline fallback reads `invoice_data.firs_service_id` but **defaults to `A8BM72KQ`** and the external flow doesn't inject the tenant's `firs_service_id` from `tenants.json`. (Doc defers IRN correctness to Relay — tracked here so it's not lost.) | **Relay** |

## Open confirmations (not blockers for the doc)
- **Public host/gateway:** the doc uses `https://api.pronalytics.ng` path-routing `/api/auth/*`→HeartBeat and `/api/ingest|status|health`→Relay. Confirm the gateway/DNS fronts both services this way (HeartBeat's OAuth + JWKS endpoints must be externally reachable).
- **`scope` value:** doc uses `invoice:submit` (per OAuth spec §3.2). Confirm this is the only external scope, or add `invoice:status` if status is separately scoped.

## Sequencing note
Gap **#1 (HeartBeat OAuth)** unblocks **#2 (Relay validation)**; until both land, external auth physically can't be OAuth. If a working integration is needed before OAuth ships, the interim is the live **3-header HMAC** (`X-API-Key`/`X-Timestamp`/`X-Signature`, `api_key:ts:sha256(body)`) Relay already implements — but per ARCH that is internal-only and not what the external doc should teach. Decision for ARCH/Bob: ship OAuth first, or publish an HMAC interim addendum.
